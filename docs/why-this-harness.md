# 为什么需要 Antigravity Harness

本项目针对维护者实际遇到的执行偏离、验证漂移与完成状态误判。它不宣称
Antigravity 普遍不可靠，也没有足够样本支持“某百分比任务漂移”的统计结论。
强约束是本项目的工程选择，不是给模型能力打分。

## 1. 提示词约定不等于执行边界

智能体可能正确复述目标，却在后续操作中扩大范围或改动未约定文件。
Contract 记录 objective、non-goals、allowed paths、预算、required checks 和批准触发条件。
范围脚本可依据实际基线差异观察改动，而不只相信代理自报的文件数。
但未调用的脚本没有执行效果；同用户任意进程也不受完整隔离。

## 2. 做过某个动作不等于完成任务

Created/Ran 标签、工具被调用、宿主 Post、进程退出、测试通过、需求验收是不同层级。
本项目分开 Attempt 和 Tool Operation，保持真实退出码和未知结果，不从成功字样推断事实。
源代码完成门控只能到 checking；缺少或失效的证据仍是 unverified。

## 3. 旧证据不能替新代码背书

历史验收曾引用一个后来被修改的输出文件，导致原链条无法完整重验。
正确处理是保留失效事实，并在未来尝试中使用固定证据快照，而不是改写旧哈希、
删除失败 Attempt，或挑一个“最新成功结果”替代原来的明确引用。
[历史准入说明](production-readiness.md)保留了这个例外；它也说明门控确实会拒绝不完整链条。

## 4. 内联询问在某次现场观察中没有成为可靠门槛

2026-09-08 的特定 Desktop 环境中，预期 force_ask 会请求确认并阻止未批准写入，
但观察到没有确认、写入仍发生。项目随后在相应受保护场景改用明确 Binding 和 deny。
这不证明所有版本或所有询问机制都有同样问题，缓存或宿主行为的确切根因未确认。
[脱敏现场说明](live-session-binding-force-ask-failure-20260908.md)

## 5. 不完整观察必须保持未知

某些记录缺少匹配 Post；另一些宿主返回值与请求的子进程退出码不同。
不能补造事件，也不能仅凭这些现象断言具体哪一层发生了转换或丢失。
当前 v4 使用保守分类：unresolved / unclassified 不自动成为成功。
历史文档描述的是当时观察和探索，当前行为以 v4 实现为准。

## 6. 为什么不对 Antigravity 做同样的减负

Codex 侧减负针对其自行完成的普通工作，不取消现有项目验收。
Antigravity 侧的主要需求是控制执行漂移，因此保留强约束、fresh hashes 与完整必需检查。
即使交给 Codex 审核，产物来源的严格要求也不会下降。

## 不应从本项目推出的结论

- 哈希不是数字签名，角色名称不是可信身份。
- guarded 不是全功能自动开发模式；其终端／不透明子代理受限。
- strict 隔离模式不可用，不能用于宣称已防住同用户任意执行。
- 测试通过不证明模型永远遵循规则，也不证明其他 Desktop 版本行为相同。
- 本地原始证据未公开时，仓库中的脱敏摘要不是可独立核验的全部现场材料。

这种保守性是设计的一部分：能约束的行为用脚本约束，未观察到的能力明确写成未验证。
